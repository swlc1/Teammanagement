# Team Management Dashboard · Firebase 연결

GitHub Pages의 화면을 유지하면서 Firebase Authentication과 Firestore로 로그인 및 업무 데이터를 공유합니다. 별도 npm 빌드 없이 `index.html`, `sync-engine.js`, `firebase-backend.js`를 같은 경로에 배포합니다.

## 적용 순서

1. 이 변경사항을 `main`에 병합합니다. GitHub Pages 배포가 끝나면 `https://swlc1.github.io/Teammanagement/`를 새로고침합니다.
2. Firebase 프로젝트 `teammanagement-1a1f2`의 Firestore 규칙을 이 저장소의 `firestore.rules` 전체 내용으로 교체하고 게시합니다. 이전에 설정한 관리자 전용 규칙으로도 첫 관리자 확인은 가능하지만 팀장·팀원 운영에는 새 규칙이 필요합니다. GitHub에 규칙 파일을 올리는 것만으로 Firebase에 적용되지는 않습니다.
3. Authentication에 이미 생성한 관리자의 실제 이메일·비밀번호로 로그인합니다. `admin/admin123` 같은 기존 데모 계정은 사용하지 않습니다.
4. 관리자 문서는 `users/X5VfKprPWkgponOX3L1zPDmXn0K3`입니다. `role`은 문자열 `admin`, `enabled`는 boolean `true`여야 합니다.
5. 처음에는 업무 데이터가 비어 있습니다. 관리자 설정의 **기존 PC 데이터 가져오기** 또는 **백업 데이터 복원**으로 기존 데이터를 가져오거나 새 팀원과 업무를 등록합니다. 기존 브라우저 저장소는 자동 삭제하거나 업로드하지 않습니다. 예제 데이터가 섞였는지 확인한 뒤 가져오세요.

## 팀원 계정

1. 대시보드의 팀원정보에 팀원을 등록합니다.
2. Firebase Authentication → 사용자 추가에서 실제 이메일 계정을 만듭니다. 초기 비밀번호는 콘솔에서 직접 설정합니다.
3. 대시보드의 관리자 설정 → 로그인 계정 관리 → 해당 팀원의 **계정 연결**에서 UID와 이메일을 입력하고 역할을 선택합니다.
4. 해당 이메일로 로그인하면 연결된 팀원의 데이터를 사용합니다. 직책 변경과 로그인 권한 변경은 별도입니다.

계정 사용중지와 잠금은 `users` 문서에서 데이터 접근을 막습니다. Authentication 계정 자체의 삭제·이메일 변경은 Firebase 콘솔에서 처리합니다. 비밀번호 재설정 버튼은 재설정 메일을 요청합니다. 기존 로컬 계정의 비밀번호·해시를 Firestore로 옮기지 않습니다.

| 역할 | 데이터 접근 |
| --- | --- |
| 관리자 | 업무 데이터 전체와 계정·권한 설정 관리 |
| 팀장 | 업무 데이터 관리와 상담·면담 조회. 계정·권한 설정과 팀원정보 수정은 관리자 담당 |
| 팀원 | 허용된 메뉴 데이터 조회. 편집 권한이 있는 메뉴에서 본인 담당 기록만 수정 |

상담·면담과 시스템 로그는 관리자·팀장에게만 제공합니다. 팀원에게 상담 메뉴를 표시하도록 설정하더라도 상담 원문은 읽을 수 없습니다. 팀원은 자신의 휴가를 `신청` 상태로 등록하며 승인 상태 변경은 관리자·팀장이 처리합니다. 메뉴별 데이터 조회는 해당 메뉴의 Firestore 컬렉션 단위입니다. 메뉴를 숨기면 홈의 연관 집계도 줄어들 수 있습니다.

## 첨부파일·프로필 사진·월 추진업무 PDF

일반 업무 데이터와 로그인은 Authentication과 Firestore를 사용합니다. 파일 업로드는 별도로 Firebase Storage가 필요합니다.

1. Storage를 활성화하고 기본 버킷 `teammanagement-1a1f2.firebasestorage.app`을 만듭니다. Storage 사용에는 Blaze 요금제와 결제 계정 연결이 필요합니다. 업로드 기능 때문에 요금제를 자동 변경하지 않습니다.
2. Storage 규칙을 `storage.rules` 내용으로 교체하고 게시합니다. Firestore 권한 조회에 필요한 연동 권한을 콘솔에서 요청하면 허용합니다.
3. 다운로드에 사용하는 `getBlob()`을 위해 버킷 CORS에 사이트 출처를 허용합니다. Google Cloud CLI를 사용할 수 있는 환경에서 다음을 실행할 수 있습니다.

```bash
gcloud storage buckets update gs://teammanagement-1a1f2.firebasestorage.app --cors-file=storage.cors.json
```

파일당 최대 10MB입니다. 원본 파일은 Storage에 두고 Firestore에는 경로와 메타데이터를 저장합니다. 프로필 사진과 PDF 뷰어는 호환성을 위해 다운로드 토큰 URL을 사용합니다. 해당 URL을 전달받은 사람도 접근할 수 있으므로 외부 공유를 제한해야 하는 문서에는 이 뷰어를 사용하지 마세요. 파일 교체·기록 삭제 시 이전 원본은 백업 연결을 보존하기 위해 자동 삭제하지 않습니다. 용량 정리는 관리자가 Storage 콘솔에서 처리합니다. JSON 백업에는 파일 원본이 들어 있지 않습니다.

Storage를 활성화하지 않으면 첨부파일 없는 업무 등록·수정은 사용할 수 있습니다. 업로드 실패 시 저장 성공으로 표시하지 않으며 입력창을 유지합니다. 사진이나 PDF가 포함된 기존 데이터의 가져오기에도 Storage가 필요합니다.

공식 참고: [Storage 결제 요구사항](https://firebase.google.com/docs/storage/faqs-storage-changes-announced-sept-2024), [다운로드 및 CORS](https://firebase.google.com/docs/storage/web/download-files).

## 저장과 충돌

- 각 업무·일정·사업 등을 별도 문서로 저장합니다. 데이터베이스 전체를 한 문서에 덮어쓰지 않습니다.
- 각 기록의 버전을 트랜잭션에서 확인합니다. 다른 사용자가 같은 기록을 먼저 변경하면 후속 저장을 중단합니다.
- 왼쪽 아래에 서버 저장 상태가 표시됩니다. 실패한 변경사항은 화면 메모리에 유지됩니다. **미저장본 다운로드**로 복사한 뒤 서버 내용으로 되돌리거나 연결 복구 후 다시 저장할 수 있습니다. 브라우저 종료 경고를 무시하면 미저장 변경사항이 사라집니다.
- 여러 기록의 일괄 삭제와 백업 복원은 기록별로 처리합니다. 중간 실패 시 앞서 저장된 기록은 반영되어 있을 수 있습니다. 상태창에서 남은 변경사항을 확인하세요.
- 로그인 정보는 브라우저 세션 동안 유지합니다. 업무 데이터는 영구 로컬 캐시에 저장하지 않습니다. 로그아웃할 때 메모리와 화면의 데이터를 지웁니다.

## 검증

```bash
node --test tests/sync-engine.test.cjs tests/adapter.test.cjs
```

동시 수정 충돌·다른 기록 보존·저장 중 추가 변경·통신 실패 재시도·삭제 충돌·로그아웃 정리 및 Firebase 어댑터의 로그인/저장/원격 갱신을 모의 SDK로 검사합니다. 어댑터 검증에서는 실제 페이지의 렌더러도 빈 DB로 실행합니다.

`tests/browser-smoke.cjs`는 Playwright 브라우저 검증용입니다. 실행 환경에 Playwright와 Chromium이 필요합니다. 이번 작업 환경에서는 Chromium 다운로드가 네트워크 제한으로 차단되어 브라우저 검증은 실행하지 못했습니다. 모의 테스트는 실제 Firebase 서비스·보안 규칙의 에뮬레이터 검증을 대신하지 않습니다. 운영 적용 후 관리자 로그인 → 업무 등록 → 다른 PC 조회 → 팀원 로그인과 본인/타인 기록의 권한을 확인해야 합니다.

서버 비밀키나 서비스 계정 JSON은 저장소에 추가하지 않습니다. 웹용 Firebase 설정값은 클라이언트에 포함되며 실제 접근 권한은 게시된 Firebase 규칙으로 제한합니다.
